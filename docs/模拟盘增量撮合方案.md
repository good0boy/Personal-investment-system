# 模拟盘「增量撮合」改造方案

> 状态：**方案待审批**（2026-10-10 起草）。主人批准前**不动任何代码**。
> 关联：`docs/策略规格说明书-v2.0-中频质量反转.md`（批准后升 v2.4）·
> `docs/部署指南-腾讯云.md`（内存评估）· 计划存档 `.workbuddy/plans/blazing-nebula-turing-IwDl-7g0.md`

---

## 0. 一句话

把模拟仿真跑批从「每晚从 2025-01-01 全量重算整段历史」改为「每晚只撮合当天一天」，
**回测引擎（全量）与模拟盘执行器（增量）分成两个类、共用同一份策略与撮合规则**。
内存峰值 3.3GB → 预计 <500MB，2核2GB 服务器可跑；跑批时长分钟级 → 秒级。

## 1. 现状与动机

| | 现状（全量重算） | 改后（增量撮合） |
|---|---|---|
| 每晚做什么 | 引擎从 2025-01-01 跑到今天（21 个月全市场） | 载入近 ~120 交易日窗口，只执行「今天」一天 |
| 峰值内存 | **3383MB**（实测，psutil 采样） | 预计 <500MB（窗口矩阵 ~1/18 + 无全历史行缓冲） |
| 耗时 | 本地 51s，服务器 2-4 分钟 | 预计秒级 |
| 2核2GB 服务器 | ❌ OOM 必现 | ✅ 可跑 |
| 语义 | "净值历史 = 每晚整体重写的快照" | "净值历史 = 每天追加一行"（与真实账户记账同构） |

为什么现在改：上腾讯云后 2GB 套餐被这一个峰值卡死；且全量重算模式还有
"补跑覆盖陷阱"（幂等闸只看日期）这类只为全量而存在的补丁。

## 2. 目标架构

```
strategies/
  engine.py          BacktestEngine（全量，回测 + 模拟盘现用）—— 不动
  paper_engine.py    PaperEngine（新，单日增量执行器）
app/services/
  paper_service.py   run_paper_day 按 paper.engine_mode 分派：full | incremental（默认 full）
```

### 2.1 共享与复用（策略与撮合规则零分叉）

- **策略零改动**：`on_bar / _sell_side / _buy_side / last_entry_candidates` 原样复用 ——
  PaperEngine 构造与 BacktestEngine 同构的 `StrategyContext`（account/market/universe）。
- **成本零分叉**：`cost_model` 全部是无状态纯函数（买入成本/卖出净额/整手数），直接调用。
- **撮合规则复用**：T+1 开盘买、T 日尾盘收盘卖、开盘涨停买不进顺延、收盘跌停/停牌卖不掉
  顺延次日开盘 —— 从 engine 抽取撮合子模块（`_fill_buy/_sellable_core/_execute_pending*`）
  供两个引擎共用（抽取时保持方法体不变，全量引擎回归测试作护栏）。

### 2.2 跨日状态持久化（新增 `state.json`，原子写）

全量模式的状态只活在引擎内存里；增量模式每晚"接着昨天跑"，以下状态必须落盘：

| 字段 | 来源 | 用途 |
|---|---|---|
| `cash` | engine.cash | 资金链 |
| `positions[]`（symbol/shares/entry_date/entry_price/entry_cost/**entry_idx**） | engine.positions | 持仓与 hold_days（= 当日矩阵 idx − entry_idx + 1，含首尾） |
| `last_sell_date{}`（禁买 60 日窗口） | engine.last_sell_date | 卖出后禁买回看 |
| `pending[]`（顺延订单：涨跌停/停牌未成交的买卖单，含 retries） | engine.pending | 跨日存活 |
| `cummax_nav` | nav 历史 | drawdown 增量计算 |
| `benchmark_base` | 序列首日指数 close | benchmark_nav 增量对齐 |

### 2.3 每晚执行序列（PaperEngine.run_one_day(run_date)）

复刻全量引擎单日 6 步（engine.run() L1028-1097），只是循环长度 = 1：

1. 载入窗口矩阵：行情 `[run_date−120 交易日, run_date]`（preheat 实测 97 交易日 + 余量，
   覆盖 ret_50 因子由因子文件承担、禁买 60 日回看、新股 90 日门槛、门1 指数近 20 日）；
2. `_execute_pending`：开盘撮合昨日挂单（T+1 买 + 顺延卖单按开盘价重试）；
3. `_set_total_asset`：收盘价标记总资产；
4. `strategy.on_bar(ctx)`：当日决策（卖出判定 6+2 条 + 每 rebalance_every 日的建仓评估，
   `last_entry_candidates` 天然就是当天的）；
5. `_execute_pending_at_close`：尾盘按收盘价撮当日卖单；
6. `_mark_and_snapshot`：当日 equity/positions 行 → **追加**进 nav/positions；
   当日 trades/orders 行 → 追加；`metrics/config.json` 整体重写（本来就是全期统计）；
   `state.json` 原子写。

### 2.4 全量模式的保留职责（不删）

- **冷启动/重建**：`state.json` 缺失或损坏 → 自动落回全量重算一遍重建状态；
- **策略切换**：`_invalidate_paper_artifacts` 照旧删产物 → 下一次全量重算；
- **对拍基线**：影子双跑的对照面。

## 3. 已识别风险与对策（按对拍难度排序）

### 3.1 退市强平的语义反转 ★ 最难的一致性点

- **全量模式**：`_derive_last_data_di` 用**未来数据**（矩阵里每只标的最后一次有行情的位置）
  判"数据终止 N 日 → 强平"。
- **增量模式**：`run_date` 之后没有数据，这个判定**永不触发** → 退市股挂账。
- **对策**：增量模式改用**显式退市事件源**：持仓标的在 universe 快照连续消失 +
  行情连续 `delist_confirm_days` 日无 K 线 → 强平。两模式在"确认延迟"上**天然有 1-3 日时点差**
  —— 方案是对拍时允许该类别差异（逐笔核对、确认仅时点不同），或全量模式同步改造为
  事件源口径（更彻底，动回测语义，需单独批准）。
- **现状校验**：quality_reversal 持仓 30 日内必然 time_stop 换手，实际触发退市强平的
  概率极低（2025-01 至今 trades 里 delist 出场占比待查）—— 影响面小但要记录在案。

### 3.2 浮点累加顺序

`cash/total_asset` 的复利路径对运算顺序敏感（1e-7 级差异被 nav 复利放大）。
对策：PaperEngine 的记账顺序**逐行复刻** engine 的 `_fill_buy/_settle_sell/_set_total_asset`
运算次序；对拍门槛 `assert_frame_equal(check_exact=True)`，不允许 rtol。

### 3.3 停牌持仓重估

`_price_or_last`（最近可用收盘价）估值 —— 增量模式从窗口矩阵取价，
必须与全量取到**同一个"最后可用价"**。窗口 ≥120 交易日 > 最长停牌观察期，覆盖成立。

### 3.4 截面统计的全池依赖

`rank(pct=True)`、低波/低换手中位数门、门1 指数涨幅 —— 都是**当日全池截面**，
增量下只要拿到当日全池因子行即可（因子文件本来就是全历史）；但**股票池构建**
（上市 90 日、禁买 60 日、limit_up 近 N 日触板）需要窗口矩阵 —— 120 日窗口覆盖。

### 3.5 pending 与禁买窗口

顺延卖单（跌停卖不掉）跨日存活、禁买 60 交易日回看 —— 全靠 `state.json` 持久化，
不重放推导（orders 重放会混入 rejected/pending/filled 状态，易错）。

## 4. 上线硬门槛：一致性对拍

1. **合成数据逐位对拍**：同一份合成数据（复用 test_quality_reversal 夹具，日历加密到逐日），
   「全量 engine.run()」vs「逐日调 PaperEngine」，5 份产物 `assert_frame_equal(check_exact=True)`；
   退市强平时点差按 §3.1 的白名单规则单独核对。
2. **生产影子双跑 ≥20 个交易日**：`paper.engine_mode=full` 继续为准，
   增量路径并行执行（只写影子目录、不对外），每晚比对 5 份产物逐位一致。
3. 对拍全绿 → 切 `engine_mode=incremental` → 观察 2 周 → 复盘后清冗余。

## 5. 测试与回归预告

- **需重写**：`test_run_paper_day_second_run_overwrites`（"再跑晚日期覆盖而非追加"与追加语义冲突）、
  `test_run_paper_day_full_pipeline` 的 nav 行数断言、幂等闸注释语义；
- **保持**：前端契约（当前净值=曲线最后一点、最近交易=平仓∪持仓）、策略全部单测、
  `test_same_config_two_runs_identical`（全量引擎确定性）；
- 新增：PaperEngine 单元（状态载入/追加/自愈回退）+ 对拍套件。

## 6. 预期收益与成本

| 项 | 估计 |
|---|---|
| 开发 | PaperEngine + state 持久化 + 撮合抽取 ≈ 3-5 个工作日量级（含对拍套件） |
| 风险 | 中 —— 最大的不确定性在退市时点差与浮点对拍，均有明确对策 |
| 收益 | 2GB 服务器可跑（省 2 档套餐差价）、跑批秒级、记账语义与真实账户同构 |
| 代价 | 新增 state.json 一份状态产物；全量路径保留（冷启动/自愈/对拍） |

## 7. 需要主人拍板的点

1. **是否批准实施**（本方案批准后：先改规格书升 v2.4 → 再动代码 —— 纪律不变）；
2. **退市强平口径**：接受增量模式的"确认延迟时点差"（推荐，改动小），
   还是连回测引擎一起改为事件源口径（更彻底，动回测语义）；
3. **切换方式**：影子双跑 ≥20 交易日后切换（推荐），还是直接切（不推荐）。
