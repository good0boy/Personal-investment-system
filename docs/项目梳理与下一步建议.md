## 二、这是什么系统

**一句话**：一个"**只读展示层 ＋ 日度调度器**"。计算全在 CLI 里跑完落盘，Web 只负责把结果画出来。

| 模块 | 本质 | 数据来源 | 交互 |
|---|---|---|---|
| **1 数据分类** | 接口目录浏览器 + 在线试跑 | akshare（广度，1083 个函数）+ baostock | 有"试跑"按钮（唯一触发真实网络调用的入口） |
| **2 因子库** | 离线算好的因子 → 可视化 | `factors/calc.py` CLI 落盘 | 只读 |
| **3 策略回测** | 离线跑好的回测结果 → 可视化 | `strategies/run.py` / `sweep.py` CLI 落盘 | **只读，无"运行回测"按钮（是设计）** |
| **4 模拟仿真** | 日度跑批 + 净值落盘 | 调度器 23:00 触发，全量重算 | 只读 + 手动入队触发 |
| **5 用户提醒** | 事件 → 企微推送 | 模块 4 的 `orders.parquet` | 有"发测试消息"按钮 |

**三条决定架构的判断（仍成立，别推翻）**：
1. 模块 1/3 不需要后端计算，只需读本地文件 → 前端与策略彻底解耦。
2. **不引入数据库服务**：Parquet + DuckDB（分析型）＋ SQLite（事务型）＋ YAML（配置），零运维。
3. 计算密集任务（回测 / 寻优 / 因子计算）**走 CLI 不走 Web** → 页面永远毫秒级响应。

## 五、四条关键契约（破坏任一条 = 返工）

### 1. 文件契约（模块 3 的前后端唯一耦合点）

```
data/backtest/{strategy}/{run_id}/
├── equity.parquet   date, nav, benchmark_nav, drawdown, position_count, cash_ratio
├── trades.parquet   date, symbol, name, side, price, shares, amount, fee, pnl, reason
├── orders.parquet   委托流水（模块 5 的提醒事件源头）
├── metrics.json / config.json / run_meta.json
```

好处：策略改了不用重新部署系统；结果可直接归档、跨版本对比；系统挂了不影响跑策略。

### 2. YAML 契约（"配置进 YAML，状态进文件/DB"）

- 定义类 → YAML：`factors/registry.yaml`（因子）、`catalog/*.yaml`（接口目录）、
  `sweeps/*.yaml`（寻优网格）、`datasource_capabilities/*.yaml`（能力矩阵）、`alert_templates.yaml`
- 状态类 → 文件：`data/factor/_manifest.json`、`data/backtest/.../run_meta.json`
- 事务类 → SQLite：`alert_log`（幂等键）、`job_run_log`、`paper_account`

**纪律 6：不搞双份真相。**（已为此删掉过 `datasource_capability` 与 `factor_registry` 两张死表）

### 3. 架构纪律八条

① 数据源只能走 `data_source/` ② 文件 IO 只能走 `data_store.py` ③ 成本只能走 `cost_model.py`
④ 模块 3 前端只读文件 ⑤ 计算密集走 CLI 不走 Web ⑥ 配置进 YAML / 状态进 DB（因子状态也走文件）
⑦ "刷新/探测"类方法必须 `force_refresh` 绕过缓存 ⑧ 因子口径只写在 `registry.yaml`，代码不得按因子名 if-else

### 4. 数据正确性红线

后复权 hfq 统一 · 信号 T 日收盘 → **T+1 开盘成交** · 读取上界 `min(时间锁, 今天)` ·
ST/停牌用 baostock 逐日 `isST`/`tradestatus` · 纳入退市股（消除幸存者偏差）·
跌停/停牌**不按理想价撮合、顺延** · 新股入池 90 交易日 ≠ 禁卖窗口 60 交易日（两个独立参数）·
止盈判定扣成本（净 10% ≈ 毛 10.22%/10.28%）

### P0 — 高价值，建议优先

#### P0-1 ⭐ 启用 `fundamental` 因子分类（数据已就位，只差实现）

- **为什么**：2.1 GB 财务数据已经躺在盘上（含**公告日 `NOTICE_DATE`**，工具已按"公告日第一公民"
  设计，缺失时回退 `report_date+90 天` 的保守口径 —— 未来函数防线已在数据层做好）。
  但现在 `registry.yaml` 把整个分类标成 `blocked`、前端显示"数据源未接入"。
  **这是一份已完成却没被使用的资产。**
- **做什么**：① 把分类 `status` 从 `blocked` 改为 `ready`；
  ② 在 `factors/impl/` 下写财务类因子（建议先做 4~6 个高信息量的：
  `roe_ttm` / `pe_ttm_rank` / `net_profit_yoy` / `revenue_yoy` / `gross_margin` / `debt_ratio`）；
  ③ 按 `notice_date` 对齐（**不是** `report_date`）；④ 跑 `calc` + `analyze` 看 IC。
- **代价**：约 1~2 人日。**零架构改动**（因子库的设计就是"加函数 + 加 YAML"）。
- **验证点**：`python -m factors.calc --category fundamental` 能出产物；前端分类卡片从"待接入"变可点。
- **风险**：报告期与公告日之间可能有 1~4 个月滞后 → 因子经济含义要在 YAML 的 `desc` 写清。

#### P0-2 ⭐ 因子去相关后合成（研究文档 §5 唯一剩余项）

- **为什么**：§3.2 已实测 11 个因子只坍缩成 **约 3 个独立维度**
  （动量簇 ρ≈0.89 / 活跃度簇 ρ≈0.87 / `today_pct` 独立）。
  继续堆同族因子是重复计数；**跨簇合成才是唯一可能产生新信息的方向**。
  §3.1 又证明"降频"和"取负"都不通，所以合成几乎是剩下的主路径。
- **做什么**：① 每簇选一个 IC 最强的代表（如 `max_ret_20` + `volatility_20` + `today_pct`）；
  ② 用**逐日截面秩**标准化后等权/IC 加权合成 combo 因子；③ 走同一套 `analyze` 看分层与 IC，
  **重点看 G1~G4 是否整体抬升、G5 是否不再单独崩坏**。
- **代价**：约 1 人日（`factor_correlation.json` 与合成工具的基础都在）。
- **注意**：合成属于新增因子，不改策略规则；但**若之后要把它接进策略**，那就是改规则 → 先改规格书升版本。

#### P0-3 补 `data/raw/universe/` 股票池快照落盘

- **为什么**：从研究文档 §1 就挂着至今。基准目前只能用 `quote_daily` 全量凑，
  **口径与回测内的股票池（剔除 ST/停牌/新股/一字板）不一致** —— 而"没有基准不动结论"是头号纪律，
  基准口径不严等于纪律打折。
- **做什么**：在 `strategies/engine.py` 或 `tools/universe.py` 侧落一份逐日股票池快照
  （`date` + `symbol` 列表），基准计算改用它。
- **代价**：0.5 人日。
- **收益**：之后所有"策略 vs 基准"的结论都可被严格复算。

|---|---|---|
| P2-1 | 日志表保留策略 | `datasource_log`/`job_run_log`/`alert_log` 无限增长（补一次数据 5000+ 行） |
| P2-2 | 因子产物 `value` 降 float32 | 11 个因子已 540 MB；因子数上 30+ 再动（现在 float64 让手算校验零误差，价值更大） |
| P2-3 | 3 个无消费者接口 + 死代码 | `GET /catalog/tree`、`/catalog/check/status`、`calendar_service.is_weekend` 等 |
| P2-4 | 清理 `backend/` 下运行残留 | `.uvicorn*.log`、`sweep_smoke.log`、`.pytest_cache`、`.ruff_cache` |
| P2-5 | `docker compose up` 实跑一次 | 决策 #35 一直挂着；**上线前必做** |

### 明确**不建议**做的（有证据支撑的"不做"）

| 想法 | 为什么不做 |
|---|---|
| 把动量信号**取负** | §3.2 实测：G1~G4 毛年化齐平 +18%~+23%，只有 G5 单独崩坏。取负会把 G1~G4 的优势一起做反 |
| 继续**调参**（持有期/止盈） | 12 组寻优无一为正、无单调性；两期归因一致 → 不是参数问题 |
| **降频**救成本 | §3.1 实测 h1→h5→h10 亏损**放大**而非衰减，且两端换手本来就低（成本几乎不变） |
| 换**成交时点**（T 收盘成交） | 边际分解：隔夜跳空本身 -1.8%，改时点会让口径更差 |
| 上 ClickHouse / PostgreSQL | 2,600 万行、单用户，属严重过度设计（技术架构 §5.0 已论证） |

## 八、开工前的固定动作（建议固化成习惯）

```bash
# 1. 环境是否完好（换机器后第一次）
双击 setup.bat                      # 建 .venv + 装依赖；幂等

# 2. 质量门（改代码后必跑，三项都要过）
cd backend && .venv\Scripts\python.exe -m pytest -q && .venv\Scripts\python.exe -m ruff check .
cd frontend && npm run build

# 3. 起服务
双击 start-dev.bat                  # 开发；注意首启会补跑历史交易日（端口后开）
双击 start-service.bat              # 服务模式：单端口跑整站（SERVE_FRONTEND=1）

# 4. 验证
GET http://127.0.0.1:8000/api/health     # status 应为 ok
```

**判断后端是否真的起来了**：看窗口有没有打印 `启动完成` / `Application startup complete`。
只打印到 `[paper_daily] 检测到 N 个缺失交易日` 就说明**正在补跑**，端口还没开。
