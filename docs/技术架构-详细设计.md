## 5. 数据层设计

### 5.0 为什么是「Parquet + DuckDB + SQLite」

这不是随手选的，先算清楚数据量，再逐项对比。

#### 数据量到底有多大

| 数据 | 估算 |
|---|---|
| 全 A 股股票数 | ~5,400 只 |
| 每年交易日 | ~242 天 |
| 20 年日线总行数 | 5400 × 242 × 20 ≈ **2,600 万行** |
| 每行字段数 | 12 列（OHLCV + 复权 + 涨跌幅等） |
| CSV 体积 | ~3~5 GB（无压缩） |
| **Parquet 体积（zstd）** | **~400 MB ~ 1 GB** |
| 内存中（pandas） | ~2~3 GB（float64 为主，可降精度） |

**结论**：这是一个**「单机能装进内存、但 CSV 存着难受」**的量级。这个判断决定了后面所有选择。

#### 为什么是 Parquet（而不是 CSV / HDF5 / 直接入库）

| 对比项 | CSV | **Parquet** | HDF5 | 塞进 SQLite |
|---|---|---|---|---|
| 体积 | 3~5 GB | **0.4~1 GB** | ~1 GB | 2~3 GB |
| 是否带类型 | ❌ 全字符串，每次读都要推断 | ✅ 强类型，含 decimal/date | ✅ | ✅ |
| 列裁剪 | ❌ 必须读全列 | ✅ **只读需要的列** | ⚠️ 有限 | ✅ |
| 分区裁剪 | ❌ | ✅ **`year=2024/` 直接跳过其他年份** | ❌ | ❌ |
| 谓词下推 | ❌ | ✅ **自带 min/max 统计，跳过不匹配的行组** | ❌ | ⚠️ 需索引 |
| 读取速度 | 慢（解析字符串） | **快 10~50 倍** | 快 | 中（行存扫描） |
| 并发写 | ❌ 无锁 | ⚠️ 靠"整体覆写"回避 | ❌ **多进程写会损坏文件** | ⚠️ 单写者锁 |
| 开放格式 | ✅ | ✅ 已是事实标准（Spark/Arrow/大厂数据湖） | ⚠️ 生态在萎缩 | ✅ |
| 10 年后还能读吗 | ✅ | ✅ | ⚠️ 需特定库版本 | ✅ |

**决定性的一条**：Parquet 是**列存 + 带统计信息**。我要查"茅台 2024 年的收盘价"时，DuckDB 会：
1. 目录级跳过所有 `symbol != 600519` 的文件
2. 文件内靠 row group 的 min/max 跳过不相关的数据块
3. 只解压 `date, close` 两列

整个过程可能只扫几 MB。CSV 做不到其中任何一条——必须读 3 GB 然后过滤。

#### 为什么是 DuckDB（而不是 MySQL / PostgreSQL / ClickHouse / 或者直接 pandas 读）

**DuckDB 的核心价值：它是一个"进程内的列式 SQL 引擎"，可以直接对 Parquet 文件跑 SQL，不需要建库、不需要导入、不需要起服务。**

```sql
-- 这一句就能查三年全市场数据，不用导入、不用建表、不用索引
SELECT symbol, avg(close) FROM 'data/raw/quote_daily/**/*.parquet'
WHERE date BETWEEN '2024-01-01' AND '2024-12-31' AND symbol = '600519'
GROUP BY symbol;
```

| 对比项 | **DuckDB** | MySQL/PG | ClickHouse | 纯 pandas 遍历读 Parquet |
|---|---|---|---|---|
| 要不要装服务 | **不要**（一个文件/一个库） | 要装、要配、要备份 | 要装，吃内存 | 不要 |
| 要不要 ETL 导入 | **不要，直读 Parquet** | 要写导入程序 | 要写导入程序 | 不要 |
| 查询语言 | **完整 SQL** | SQL | SQL | ❌ 手写 pandas |
| 聚合性能（2600万行） | **0.1~1 秒** | 1~10 秒（行存扫描） | **最快**，但过重 | 0.5~5 秒，且吃内存 |
| 内存占用 | 低（流式、可外存） | 低 | **高（通常 ≥16G 起）** | **高（全量入内存）** |
| 运维成本 | **≈0** | 中 | 高 | 0 |
| 适合场景 | **单机分析，正好** | 多用户 OLTP | 海量分析 | 小数据/一次性脚本 |

**为什么不用 pandas 直接读**：pandas 的模型是"全量读进内存再算"。查全市场 20 年数据要 2~3 GB 内存，且每次查询都要重新加载。DuckDB 可以流式处理、只物化结果。而且 SQL 写复杂聚合比 pandas 链式调用清晰得多。

**为什么不上 ClickHouse**：它是为"十亿行以上、多用户并发、集群"设计的。你这里 2600 万行、单用户，属于**严重过度设计**——为了省一点查询时间，付出一个常驻服务 + 至少 16 GB 内存 + 运维成本。

#### 为什么是 SQLite（而不是也用 Parquet，或者也用 DuckDB）

**关键在于：不同数据的访问模式完全不同。**

| | 大表时序数据（行情/因子/净值） | 元数据（目录/注册表/日志/运行记录） |
|---|---|---|
| 行数 | 千万级 | 几十~几万 |
| 访问模式 | 范围扫描 + 聚合，**批量读** | 按主键点查、**增删改**、多表关联 |
| 写入模式 | **整体覆写**（一次性写一个分区） | **频繁小事务**（每跑一次回测写一条） |
| 需要事务吗 | 不需要 | **需要**（幂等键、状态机、并发保护） |
| 需要改单行吗 | 不需要 | **需要**（`alert_log.status` 从 pending 改 sent） |

**Parquet 的根本短板是"不能改单行"**——它没有 UPDATE/DELETE，改一行要重写整个文件。用它存"提醒日志"是错的：你想把一条消息的状态从 `pending` 改成 `sent`，得重写整个文件。

**SQLite 正好补上这个短板**：

- **单文件、零运维**：`meta.db` 就是一个文件，跟 Parquet 一样好拷好备份。
- **完整事务**：`alert_log` 的幂等靠 `UNIQUE(event_key)` + 事务保证；模拟盘跑批的"先删后插"靠事务保证。
- **点查极快**：几万行以内，带主键索引的点查是微秒级。**这个量级下 SQLite 比任何服务型数据库都快**（因为省掉了网络往返）。
- **不用 DuckDB 存元数据的原因**：DuckDB 强在 OLAP（批量分析），它的写入是"追加式"的，单行 UPDATE 的并发和事务模型不如 SQLite 成熟。**元数据是 OLTP 场景，SQLite 是对的选择。**

#### 分工总结

```
                    写入模式          访问模式            选型
行情/因子/净值   →  整体覆写一次   +   范围扫描聚合     →  Parquet + DuckDB
                                                              （列存 + SQL）
元数据/日志/状态 →  频繁小事务     +   点查 + 关联      →  SQLite
                                                              （行存 + 事务）
人工配置         →  人工编辑       +   全量加载         →  YAML
                                                              （可读 + 可 diff）
```

**一句话**：**分析型数据用列存（Parquet + DuckDB），事务型数据用行存（SQLite）。把它们混在一起，无论用哪个方案都会难受。**

#### 这个方案的好处（具体点）

1. **零运维**：不需要装任何数据库服务，不需要配连接池、不需要做数据库备份策略。整个 `data/` 目录就是全部数据，`cp -r` 就是备份。
2. **备份一致性简单**：Parquet 是只读追加/覆写，SQLite 打包时用 `VACUUM INTO` 拿一致性快照，两者不在同一事务里也不会互相破坏。
3. **数据可移植**：Parquet 和 SQLite 都是开放格式且有十几年生命力。就算这套系统将来废弃，数据能用 pandas / Excel / 任何工具直接读出来。
4. **本地开发与服务器部署完全一致**：不需要"本地 SQLite、线上 MySQL"的双环境适配，容器里挂载同一个数据卷即可。
5. **调试友好**：出问题可以直接用 DuckDB CLI 或 DB Browser for SQLite 手工查，不用连服务。

#### 什么时候这套方案会不适用

诚实地说清楚边界，避免将来踩坑：

| 触发条件 | 该换成什么 |
|---|---|
| 数据量超过 **10 亿行**（如全市场分钟线全量落库） | ClickHouse / Parquet + Spark |
| 需要**多人并发写**（多账户模拟盘、多用户下单） | PostgreSQL |
| 需要**实时高频写入**（tick 级行情流） | 时序库（TimescaleDB / InfluxDB） |
| 需要**跨机分布式查询** | 数据湖 + Trino/DuckDB 集群 |

**你现在的需求一条都不沾。** 但如果将来模块 4 从"单人一个模拟账户"扩到"多人多账户在线",第 2 条就会触发——那时再把元数据从 SQLite 换成 PostgreSQL，因为已经隔离在 `repos/` 层，改动是局部的。

### 5.1 存储职责划分

| 存储 | 存什么 | 为什么 |
|---|---|---|

| **`.env`** | 密钥（企微 webhook key / corp_secret） | 不进 git |

### 5.4 复权处理（**最容易踩的坑，必须一次做对**）

三个概念要分清，用错会导致回测收益完全失真：

| 类型 | 定义 | 适用场景 |
|---|---|---|
| 不复权 `""` | 原始成交价 | 展示真实历史成交价、计算涨跌停价 |
| 前复权 `qfq` | 以**最新价**为基准调整历史 | **看图**（K线图、净值对照），但历史数据会随新除权事件变化，**不稳定** |
| 后复权 `hfq` | 以**上市首日**为基准，历史价格永久固定 | **回测/因子计算**（计算收益率必须用它） |

**结论与落地规则：**

- `data/raw/quote_daily/` 统一存 **后复权（hfq）**，用于回测和因子计算
- 前端 K 线图展示时，用同一份 hfq 数据做**归一化**（除以首日收盘价），效果等价于前复权且不会随时间漂移
- 需要展示真实成交价时，单独调 `stock_zh_a_hist(adjust="")`，**不落库**
- 涨跌停判定需用不复权价，在回测引擎里单独取

> 这条比想象中重要。用 qfq 存历史数据做回测，一年后重跑同一策略，收益率会因为新的除权事件而改变——你会发现结果不可复现。这就是"未来函数"的一种隐蔽形式。

### 5.6 股票池（Universe）过滤规则

必须在因子计算和回测入口统一执行，否则回测收益会被"理论上买不到"的股票污染：

- 剔除 ST / *ST → **用 baostock 日线的 `isST` 字段（逐日历史状态），不要用当前 ST 列表**（见 5.9）
- 剔除当日停牌 → **用 baostock 的 `tradestatus` 字段（1=交易，0=停牌）**，不要靠成交量推断
- 剔除上市不足 **90 个交易日**的新股（⚠️ 注意：这是"入池门槛"，与"卖出后 60 交易日禁买"是**两个不同参数**）
- 剔除当日一字涨停/跌停（无法成交）
- 剔除非目标板块：科创板 688、北交所（`8`/`4` 开头）、B 股（`900`/`200` 开头）

```python
# tools/universe.py —— 纯函数，回测引擎与模拟盘强制调用
LISTED_DAYS_MIN = 90      # 新股入池门槛（交易日）
NO_REBUY_DAYS   = 60      # 卖出后禁买窗口（交易日）—— 不同参数，勿混淆

def build_universe(day, market_data, meta) -> list[str]:
    """返回 day 当日可交易的股票代码列表（sh.600519 风格）"""
    codes = market_data.codes_trading_on(day)          # tradestatus == 1
    return [c for c in codes
            if is_target_board(c)                       # 沪主板/深主板/创业板
            and not market_data.is_st(c, day)           # isST == 0
            and meta.listed_days(c, day) >= LISTED_DAYS_MIN
            and not market_data.is_limit_locked(c, day) # 非一字涨跌停
            ]
```

规则写成 `tools/universe.py` 的纯函数，回测引擎和模拟盘强制调用。

### 5.7 ✅ 前视偏差：已缓解（股票池改全市场 + baostock 可拿历史成分股）

> **状态更新（v1.3）**：此问题已基本解决。解法是**双重的**：
> 1. **股票池改为沪深主板+创业板全市场**（不再依赖中证500 成分股）→ 幸存者偏差自然消除，因为退市股票的数据也在
> 2. **baostock 可以按日期查询历史指数成分股**（`query_zz500_stocks("2020-06-01")` 实测返回 500 只，`updateDate` 正确回填为 2020-06-01）→ 即使将来要用成分股，也不再是障碍
>
> 下面保留原分析作为**决策依据存档**，说明为什么最终选了"全市场池"。

#### 原问题（akshare 的限制，实测确认）

akshare 的三个成分股接口**全部不接受日期参数**：

| akshare 接口 | 返回 | 数据日期 |
|---|---|---|
| `index_stock_cons_csindex("000905")` | 500 行：成分券代码/名称/交易所 | **2026-09-15** |
| `index_stock_cons_sina("000905")` | 500 行：含「**纳入日期**」字段 | 最新纳入 2026-06-15 |
| `index_stock_cons_weight_csindex("000905")` | 500 行：含权重 | 2026-08-31 |

中证500 每半年调整一次（6 月、12 月生效），5 年调整近 10 次。用**今天的** 500 只回测 2020 年，会引入两类偏差且**方向一致偏乐观**：能提前知道哪些股票后来会涨（虚增收益），又看不到当年在成分内、后来被调出的股票（再次虚增）。

#### baostock 的解法（实测有效）

```python
import baostock as bs
bs.login()
rs = bs.query_zz500_stocks("2020-06-01")     # ← 传历史日期
# fields: updateDate, code, code_name
# 实测返回 500 行，updateDate 全部 = 2020-06-01
# 首行：["2020-06-01", "sh.600006", "东风汽车"]
bs.logout()
```

**历史成分股可以精确还原**。同理 `query_hs300_stocks("2024-06-03")` 实测返回 300 行，`updateDate = 2024-06-03`。

#### 最终选型：全市场池（理由）

即便历史成分股可得，**本项目仍选择"沪深主板+创业板全市场"作为股票池**，因为：

| 维度 | 中证500 池 | **全市场池（采用）** |
|---|---|---|
| 数据完整性 | 成分股每半年变，需维护时点快照 | 全市场数据一次拉齐，无需维护 |
| 幸存者偏差 | 需靠历史成分股消除 | **天然消除**（退市股票数据也在） |
| 与策略逻辑的匹配 | 策略实际是"选全市场强势股"，成分股限制是多余约束 | **更贴合策略本意** |
| 数据量 | ~60 万行 | ~810 万行（Parquet 200~400 MB，**可接受**） |
| 回测耗时 | 快 | 稍慢，但单机足够 |

**结论**：全市场池在方法上更严谨、维护更简单，成本仅几百 MB 磁盘。这就是最终方案。

### 5.8 数据范围与预热窗口（重要）

**业务口径是"数据从 2020-01-01 起"，恰好在 2020-05-31 之前留出了 97 个交易日的预热期**（实测），足够 20 日指标预热。回测信号从 2020-06-01 开始，所以**不需要额外提前拉数据**。

**业务口径是"数据从 2020-01-01 起"，但回测第一天（2020-01-02）就要算「近 20 个交易日涨跌幅」，需要 2019 年 12 月的数据。** 严格从 2020-01-01 起，前 20 个交易日的信号全部算不出来。

| 解法 | 做法 | 代价 |
|---|---|---|

### 5.10 数据源节流与熔断（2026-09-17 新增）

**问题**：免费数据源没有配额查询接口，只能自己约束速率。而被限频的代价不对称 ——
**限频只需一次，恢复时间却不可控**（服务端惩罚窗口可能越撞越长）。

**实现**：`services/data_source/throttle.py`，两个独立机制。

#### ① `SlidingWindowRateLimiter` —— 双约束限流

| 约束 | akshare | baostock | 说明 |
|---|---|---|---|
| `min_interval` | **1.0 s** | 0.12 s | 两次调用最小间隔，防瞬时连发 |
| `max_calls_per_minute` | **30** | 不限 | 60 秒滑动窗口内次数上限 |

两个约束**同时生效**，任一不满足则阻塞等待。注意二者不等价：
"1 秒 1 次" = 60 次/分钟，所以"30 次/分钟"其实更严格 —— **必须都实现**。

安全上限 **1800 次/小时**。按此速率拉 5000 只股票日线约需 **2.8 小时**。
这个代价是必要的：被东财封 IP 后恢复时间不可控。

#### ② `CircuitBreaker` —— 限频熔断

一旦识别到限频信号，**立即进入熔断期，期间一个请求都不发**。

| 档位 | 触发信号 | 冷却 |
|---|---|---|
| `definite` | HTTP 429 / `freq out of limit` / "访问过于频繁" | **5 分钟** |
| `soft` | `RemoteDisconnected` / `Connection aborted`（服务端掐连接） | **1 分钟** |

**为什么要分两档**：东财/新浪在限频时往往**直接掐断连接**而不返回 429。
把它算作 `definite` 会让一次偶发网络闪断拖垮整个 3 小时补数据任务；
算作普通网络错误又会持续撞墙。所以取中间：参与熔断，但冷却更短。

**熔断期间** `ensure_closed()` 直接抛 `DataSourceRateLimited`（含剩余秒数），
**根本不会发出请求** —— 也返回 HTTP 429 给前端，提示语是中文。

#### ③ 与重试的关系（关键）

**限频异常不重试。** 被限频后立刻重试等于持续撞墙。重试只针对"偶发"故障，
限频是"确定性"故障，由熔断器静默等待窗口过去。

> ⚠️ 历史 bug：重试白名单里写了内置 `ConnectionError`，而 akshare 抛的是
> `requests.exceptions.ConnectionError` —— **两者没有继承关系**，
> 导致所有网络错误都静默地不重试。现已改为**黑名单**策略
> （枚举"不值得重试"的少数几类，其余默认重试），因为第三方库的异常类型无法穷尽。

#### ④ 唯一入口纪律

限流、熔断、缓存、重试、调用日志**全部收敛在** `BaseDataSource._invoke()`。
子类发起真实请求时必须写：

```python
raw = self._invoke(
    "stock_zh_a_hist",                     # 日志用接口名
    lambda: self._run_with_timeout(_call), # 真实请求
    params={"symbol": code, "start": s, "end": e},   # 日志用参数（不得含密钥）
    cache_key=f"daily:{canonical}:{s}:{e}",          # 非 None 即启用缓存
)
```

> ⚠️ 历史 bug：这四个机制**写了但引用数全是 0**（`with_retry` / `_cache_get` /
> `_cache_set` / `log_datasource_call` 一次都没被调用，`datasource_log` 表永远为空，
> akshare 客户端限流调用 0 次）。不报错、不影响功能，只是让"保护"悄悄失效。
> 因此 `tests/test_data_source_invoke.py` 专门断言**每个机制都被真正触发**。

**观测**：`throttle_stats()` 暴露限流窗口占用、熔断状态、缓存命中数；
系统状态页与 `/api/v1/system/datasources/health` 可直接看到。

## 6. 模块详细设计

### 6.1 模块 1 · 数据分类

#### 目标
展示常用基本面 / 实时 / 历史行情接口，**入参出参示例默认收起、点击展开**，并且**参数是真实可运行的**。

#### 核心设计思想：「目录即数据」+「试跑即文档」

不要手写 API 文档页面。手写的文档一定会过时。做法是：

1. **自动生成目录骨架**：akshare 的函数都带规范 docstring（`:param xxx: 描述` / `:return: 描述`），写脚本遍历解析。
2. **在线试跑校验**：前端"试跑"按钮把参数打到后端，后端**真实调用 akshare** 并返回前 N 行。这样文档永远是真的。

#### 步骤

**S1.1 自动生成目录骨架**

```python
# tools/gen_catalog.py 核心逻辑
import inspect, akshare as ak, yaml

PREFIXES = ("stock_", "index_", "fund_")
records = []
for name, fn in inspect.getmembers(ak, inspect.isfunction):
    if not name.startswith(PREFIXES):
        continue
    doc = inspect.getdoc(fn) or ""
    sig = inspect.signature(fn)
    records.append({
        "id": name,
        "akshare_func": name,
        "params": [{"name": p, "default": str(v.default) if v.default is not inspect._empty else None,
                    "desc": parse_param_desc(doc, p)}
                   for p, v in sig.parameters.items()],
        "returns": parse_return_desc(doc),
        "doc": doc,
        "category": "unclassified",
    })
yaml.safe_dump(records, open("catalog/_raw_dump.yaml", "w", encoding="utf-8"), allow_unicode=True)
```

跑完后会得到一份**约 555 条**的原始记录（实测 1.18.94：`stock_` 403 + `index_` 78 + `fund_` 74）。这一步的价值是"不漏"，接下来的工作才是"精选"。

**S1.3 后端接口**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/catalog/tree` | 返回分类树 + 每类下接口摘要（不含入参出参） |
| GET | `/api/v1/catalog/local/datasets` | **本地数据清单**：`data/` 已落盘的维度 + 规模（文件数/体积/行数/覆盖区间）+ 汇总；`?refresh=true` 强制重扫 |

> ⚠️ `/local/*` 的路径段数（2 段 / 4 段）刻意与 `/{id}`（1 段）错开，且注册在 `/{id}` **之前** ——
> 否则以后有人把 `/local` 收成单段，会被当成某个接口 ID 去查。

`/local/*` 的实现要点（细节见 `app/services/local_data_service.py`）：

```python
# ★ 以【磁盘】为唯一真相：不读任何"登记表"
#   文件数/体积 → glob + stat
#   行数/覆盖区间 → DuckDB 读 parquet 元信息（count/min/max，不扫数据列）
#   唯一例外：因子产物的状态读 data/factor/_manifest.json（单源，不重复扫盘）
# 一次完整统计要读 ~2.5 万个文件尾（实测 12s）→ 进程内缓存 TTL 600s
# ⚠️ 行数统计的 glob 不能混 schema（equity 与 orders 的日期列名不同，DuckDB 会直接报错）
#    故拆成"行数看主表 / 体积看整个目录"，口径写进 rows_scope 字段在 UI 上如实显示
# 未落盘的维度以 available=false 出现并带原因（从回补状态文件现读，不写死在代码里）
# 示例是"一个切片"：宽表按声明列裁剪，note 里写明"共 N 列，此处展示 M 列"
```

`/try` 的实现要点：

```python
# 缓存键 = func_name + 排序后的参数，TTL 300s
# 失败时返回原始异常信息 + 提示（akshare 报错信息通常很有用）
# 单次响应截断：最多返回 100 行，最多 30 列；超出提示"共 N 行 M 列"
# 超时保护：akshare 是同步阻塞的，必须用 run_in_threadpool + asyncio.wait_for 包一层，默认 15s
```

> ⚠️ 这个 `/try` 接口是整个系统**唯一**接受任意参数并触发真实网络调用的入口。必须做：参数白名单（只允许该接口 YAML 中声明的参数名）、`symbol` 格式校验（`^\d{6}$`）、频率限制（同 IP 10 次/分钟）。

#### 策略基类（`strategies/base.py`）

> 📌 **本策略的完整规则、缺口与待确认项见 `策略规格说明书.md`。** 该文档冻结（v1.0）后，本节的 `BaseStrategy` 实现即以它为唯一依据。

**已确认的策略形态：日频截面选股 + 大盘指数择时。** 这对引擎设计有两个直接要求：

1. **必须是截面引擎**，不是单标的择时引擎。每个交易日要遍历整个股票池（中证500 ∩ 主板/创业板，约 300~500 只候选），做横截面筛选 + 排序取前 N 只。
2. **必须有仓位管理与约束层**：最大持仓数 5、单票上限 20%（按当前总资产）、新股入池门槛 90 交易日、卖出后禁买窗口 60 交易日。这些约束**不能写在策略里**，要放在引擎的 `PortfolioConstraint`，否则每个策略都要重写一遍。

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass, field

@dataclass
class BacktestConfig:
    # --- 区间 ---
    start: str = "20200601"               # 回测起点（预热窗口另配）
    end:   str = "20241231"               # 样本外日期会被 sweep.py 硬编码拒绝
    init_cash: float = 1_000_000          # 初始资金

    # --- 交易成本（★ 由 services/cost_model.py 统一实现，勿在此硬编码使用） ---
    commission_rate: float = 0.00025      # 佣金 万2.5
    commission_min: float = 5.0           # 最低 5 元
    stamp_tax_rate_pre:  float = 0.001    # 印花税 2023-08-25 前（卖出单边）
    stamp_tax_rate_post: float = 0.0005   # 印花税 2023-08-28 起（减半）
    stamp_tax_change_date: str = "20230828"
    transfer_fee_rate: float = 0.00001    # 过户费 0.001%
    slippage_bp: float = 5.0              # 滑点 5 个基点

    # --- 股票池 ---
    universe: str = "main_gem_all"        # 沪深主板 + 创业板全市场
    listed_days_min: int = 90             # ★ 新股入池门槛（交易日）
    no_rebuy_days: int = 60               # ★ 卖出后禁买窗口（交易日）—— 与上者不同，勿混淆

    # --- 组合约束 ---
    max_positions: int = 5                # 最大持仓数
    max_weight_per_stock: float = 0.20    # 单票仓位上限（按当前总资产）
    keep_cash: bool = True                # 不足 5 只时留现金，不强制满仓

    # --- 卖出规则 ---
    hold_days_max: int = 10               # 满 10 个交易日强制卖出
    take_profit_net: float = 0.10         # ★ 扣成本后净浮盈 > 10% 止盈
    index_panic_pct: float = -0.015       # 上证指数当日收盘跌幅阈值
    use_stop_loss: bool = False           # ★ 已确认不加个股止损

    # --- 择时闸门 ---
    index_code: str = "sh.000001"         # 上证指数
    timing_ret3_min: float = -0.01        # 近 3 日累计 > -1%
    timing_today_min: float = -0.005      # 当日 > -0.5%

    # --- 其他 ---
    benchmark: str = "sh.000001"          # 基准 = 上证指数
    fill_rule: str = "next_open"          # ★ T 日信号 → T+1 开盘成交

class BaseStrategy(ABC):
    """向量化策略基类：一次性拿到全历史数据，返回目标持仓矩阵。"""

    name: str = "unnamed"
    params: dict = {}

    @abstractmethod
    def generate_targets(self, data: dict[str, "pd.DataFrame"]) -> "pd.DataFrame":
        """返回 DataFrame: index=date, columns=symbol, value=目标权重(0~1) 或 目标股数"""
```

**为什么选向量化而非事件驱动**：你的策略是本地研究的，日频为主。向量化写法（`target_weights = f(close)`）比事件驱动快 100 倍以上，代码量少 90%。等真上实盘再考虑事件驱动引擎——**但净值/指标/交易记录的输出契约完全一样**，届时只需换引擎不改前端。

#### 轻量回测引擎（`strategies/engine.py`）要点

约 400 行（比通用引擎多出的部分，是**截面选股 + 组合约束**）。必须处理：

**A. 截面选股（本策略特有）**

1. **每日候选池构建**：遍历股票池，逐条套用 universe 过滤（ST/停牌/上市<60日/涨跌停/非目标板块）+ **成分股时点过滤**（`纳入日期 <= T`，见 5.7）
2. **横截面排序**：对同时符合条件的候选股排序取前 N 只（排序键见 `策略规格说明书.md` 待确认 #3）
3. **组合约束层**（`PortfolioConstraint`，独立于策略逻辑）：
   - 最大持仓数 5
   - 单票权重 ≤ 20%（按当前总资产计算）
   - 新股入池门槛 90 个交易日 / 卖出后 60 个交易日内禁买同一标的
   - 剩余资金留现金，不强平

**B. 交易与撮合（通用）**

4. **信号延迟**：T 日收盘生成信号 → **T+1 日开盘价成交**。绝不能 T 日信号 T 日收盘价成交（这是最常见的未来函数）
5. **涨跌停过滤**：T+1 开盘一字涨停不可买入，一字跌停不可卖出
6. **停牌过滤**：T+1 停牌则跳过该标的（不排队）
7. **成本计算**：买 = 金额 × 佣金率 + 过户费；卖 = 金额 × (佣金率 + 印花税) + 过户费；佣金取 `max(rate × amount, 5)`
8. **滑点**：买入价 ×(1+bp)，卖出价 ×(1-bp)
9. **整手规则**：买入股数向下取整到 100 的整数倍
10. **退市处理**：持仓股退市，按最后可交易价格强制平仓

**C. 收益率计算口径（关键）**

11. **所有涨跌幅统一用后复权 hfq 价计算**。用不复权价会在**除权日出现假跌**——把正常分红误判为下跌，直接导致漏掉信号。
    ```python
    def ret_hfq(close_hfq: pd.Series, T: int, n: int) -> float:
        return close_hfq.iloc[T] / close_hfq.iloc[T - n] - 1
    ```

**D. 可复现性**

12. 同一份 `config.json` 跑两次，`equity.parquet` 必须**逐行一致**。这要求所有排序都是**稳定排序**且排序键唯一（含代码作为末位 tiebreaker）。

#### 指标计算（`services/metrics.py`，模块 3/4 共用）

| 指标 | 公式/说明 |
|---|---|
| 累计收益 | `nav[-1] / nav[0] - 1` |

| 回撤持续期 | 从峰值到恢复的最长交易日数 |
| Calmar | `年化收益 / |最大回撤|` |
| 胜率 | 盈利交易笔数 / 总平仓笔数 |

**⚠️ 必须内置的防过拟合纪律**（写进 `sweep.py`，强制）：

1. **只用样本内数据寻优**。`sweep.py` 硬编码拒绝 `end_date > 2024-12-31`，防止误用样本外数据
2. **自动计算并输出参数敏感性**：相邻参数的表现差异超过阈值时，`summary.md` 中显式标注"疑似噪声拟合，不建议采用"

### 6.5 模块 5 · 用户提醒（框架先行）

#### 目标
接入**企业微信**，推送开仓/清仓消息。

#### ⚠️ 先说一个必须澄清的事实

**个人微信（wxid）没有任何官方推送 API。** 微信个人号不对外开放消息接口，网上所谓的"微信推送"方案要么是：
- 微信服务号模板消息 —— 需要**企业主体 + 认证服务号**（个人无法申请），且要求用户先关注
- 第三方 Hook / 逆向 —— **违反微信用户协议，有封号风险，绝不采用**

**可行且合规的路径是「企业微信」**：企业微信**个人可以免费注册**（不需要营业执照），再通过**微信插件**把企业微信的消息同步到你的个人微信里。这样你不需要装企业微信 App，个人微信里就能收到推送。

所以下面的方案全部基于企业微信，有两条路，**推荐 A**。

#### 方案对比

| | **方案 A：群机器人 Webhook** ⭐推荐 | **方案 B：自建应用** |
|---|---|---|
| 前置信息 | 只有 1 个：Webhook URL | 5 个：`corp_id` / `agent_id` / `corp_secret` / `touser` / 可信 IP |
| 审批 | 无，5 分钟搞定 | 需超级管理员建应用 |
| 服务器 IP 白名单 | 不需要（除非你主动开 IP 校验） | **必须配**，否则报 `60020` |
| token 管理 | 不需要（URL 里带 key） | 需缓存 `access_token`（7200s） |
| 消息类型 | 文本 / **markdown** / 图片 / 文件 / 图文 | 全部类型 + 可发卡片、可定向多人、可收回 |
| 频率限制 | **20 条/分钟**，无月度总量限制 | 企业级配额，宽松得多 |
| 能否发给"某个人" | 不能，只能发到群里（**自己一个人的群即可**） | 能，按 `touser` 精确指定 |
| 能否收用户回复 | ❌ 不支持回调 | ✅ 支持接收消息回调 |
| 适用判断 | 纯"给自己发通知" | 以后要交互（回复"清仓"执行指令） |

**结论**：你的需求是"给自己发开仓/清仓通知"，**用方案 A 就够了**，成本几乎为零。但**接口层要按方案 B 的形态设计**（`alert_service` 只调 `wecom_client.send(msg)`，底层可切换渠道），这样以后要加交互能力时不用改业务代码。

#### 方案 A 需要你提供的前置信息（只需 1 项）

| # | 项 | 获取路径 |
|---|---|---|
| 1 | **群机器人 Webhook URL** | 企业微信 PC 端 → 建一个只有自己的群 → 右上角 `…` → 添加群机器人 → 新创建一个机器人 → 复制 Webhook 地址<br/>形如 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxxxxxx-xxxx-xxxx` |

**注意事项**：
- 群机器人是**群维度**的，所以要先有个群。自己一个人的群完全可以用。
- **外部群不支持加机器人**；若群开了"仅群主管理"，只有群主能添加。
- 机器人有 3 种安全校验方式，**建议选「自定义关键词」**（消息里带一个固定词，如 `持仓提醒`），这样不用做签名计算、也不用配 IP 白名单。若选「签名校验」，则还需提供**安全密钥**，我需要在 `wecom_client` 里实现 HMAC-SHA256 签名。
- 若选「IP 白名单」校验，则需提供**服务器出口 IP**。
- 加机器人后如需在公司其它群复用，要"发布到公司"（仅电脑端支持）。

#### 方案 B 需要你提供的前置信息（5 项，如果你选 B）

| # | 项 | 获取路径 |
|---|---|---|
| 1 | `corp_id` | 管理后台 → 我的企业 → 企业信息 → 拉到底部「企业ID」 |
| 2 | `agent_id` | 管理后台 → 应用管理 → 自建 → 创建应用 → AgentId（一串数字） |
| 3 | `corp_secret` | 同上应用详情页 → Secret（点"查看"需验证码） |
| 4 | `touser` | 管理后台 → 通讯录 → 点进你自己的档案 → 「账号」（你的拼音或字母数字串） |
| 5 | 服务器出口 IP | 应用详情页 → 企业可信IP → 填入服务器公网出口 IP |

**配套还需做 3 个设置，否则收不到消息**（这是最常见的坑）：
1. 管理后台 → 我的企业 → **微信插件** → 用个人微信扫码关注（二维码 **7 天有效**）
2. 同一个页面：**取消勾选**「成员使用微信插件时需要使用企业微信客户端」
3. 手机企业微信 → `≡` → 设置 → 新消息通知 → **取消勾选**「仅在企业微信中接收消息」

> 注意：企业微信注册时如果**没有做企业认证**，部分能力会受限。个人注册的企业可以正常用自建应用发消息，但若后续遇到权限问题，需要走一次企业认证。

#### 接口（两套，`wecom_client` 内按渠道分发）

```
# 方案 A：群机器人
POST https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=KEY
{
  "msgtype": "markdown",
  "markdown": {"content": "**开仓提醒**\n> 标的：贵州茅台（600519）\n> ..."}
```

### A.0 ⚠️ 股票代码格式不统一（最容易踩的坑）

AKShare 各接口对股票代码的格式要求**完全不同**，没有统一约定。实测结果：

| 格式 | 示例 | 使用的接口 |
|---|---|---|
| 纯 6 位数字 | `600519` | `stock_zh_a_hist`、`stock_zh_a_hist_min_em`、`stock_zh_a_spot_em`、`stock_individual_info_em`、`stock_zygc_em` |
| 交易所前缀 + 代码 | `SZ000895` | `stock_zh_valuation_comparison_em` |
| 代码 + 交易所后缀 | `301389.SZ` | `stock_financial_analysis_indicator_em` |
| **报告期日期**（不是代码） | `20230930` | `stock_zh_a_gdhs`、`stock_fhps_em`、`stock_yjkb_em` |
| 中文名称 | `上证A股` | `stock_a_gxl_lg`、`stock_market_pe_lg` |

**对策**：在 `akshare_client.py` 里实现统一转换函数，并在每个接口的 YAML 中声明 `symbol_format` 字段，调用前自动转换。

```python
# akshare_client.py
def normalize_symbol(symbol: str, fmt: str) -> str:
    code = re.sub(r"\D", "", symbol)[-6:]          # 提取 6 位代码
    ex = "SH" if code[0] in "5689" else "SZ"       # 6/5/9/8 → 沪, 0/3 → 深
    return {
        "plain":  code,                             # 600519
        "prefix": f"{ex}{code}",                    # SH600519
        "suffix": f"{code}.{ex}",                   # 600519.SH
        "date":   symbol,                           # 原样透传
        "name":   symbol,
    }[fmt]
```

**模块 1 的 `/try` 接口必须做格式校验**：先按 `symbol_format` 转换，转换失败直接返回中文错误提示，不要把 akshare 的原始报错甩给用户。
