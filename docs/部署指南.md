# 部署指南（云服务器）

> 目标：把本项目（FastAPI 后端 + Vue3 前端 + 本地数据仓库）部署到云服务器
> （阿里云 ECS / 腾讯云轻量等均适用，当前实机：阿里云 2核4G Ubuntu 22.04），

## 0. 快速开始（TL;DR，六步）

前置：服务器已装 Docker + Compose；**本地服务已停**（避免与服务器同时补数，
baostock 配额/封禁是账号级的）。

```bash
# ① 阿里云控制台：安全组放行 80/TCP（22 应已有）。8000 不要开（只绑 127.0.0.1）
# ② 本地生成访问密码（Basic Auth，防止净值/持仓公开到公网）
cd /f/股票投资服务
bash deploy/gen-auth.sh                        # 交互输入用户名密码
# ③ 上传代码与数据（约 2.6GB，1.5~3 小时，rsync 断点续传，中断重跑即续）
bash deploy/upload-to-server.sh root@<服务器IP>
# ④ 服务器初始化（swap 4G / 时区 / 目录）
ssh root@<服务器IP>
bash /opt/stock/deploy/server-init.sh
# ⑤ 构建并启动（首次构建 3~5 分钟）
cd /opt/stock
docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml logs -f backend
# ⑥ 验证（详见 §3.1 三个断言）
curl -o /dev/null -s -w "%{http_code}\n" http://127.0.0.1/        # 401（无密码被挡）
curl -u 用户名:密码 -o /dev/null -s -w "%{http_code}\n" http://127.0.0.1/  # 200
```

浏览器访问 `http://<服务器IP>`（手机/外地电脑同样可访问，首次输一次密码）。

## 1. 实例选型（先看结论）

### 1.1 硬件要求（实测依据）

| 维度 | 需求 | 实测/依据 | 结论 |
|---|---|---|---|
| **内存** | **≥ 4GB（推荐 8GB）** | 日常跑批已改**增量撮合**（窗口 121 交易日，实测补数子进程 ~406MB、撮合秒级）；但 **state.json 丢失/首次冷启动会回退全量重算，峰值 RSS 3383MB**（psutil 实测） | ⚠️ 硬门槛（兜底路径用） |
| CPU | 2 核起步 | 跑批是 IO 型为主（东财/baostock 分页拉取），本地 2 核量级全量重算 ~1-2 分钟 | 2 核够 |
| 磁盘 | 40GB 够 | `data/` 当前 3.8GB（2.9 万 parquet）+ Docker 镜像 ~1.5GB + 系统 ~4GB，剩余 >30GB；回测产物日增 ~几 MB | ✓ |
| 带宽 | 3Mbps 够 | 单用户使用；前端首载 gzip ~1.2MB ≈ 4s；数据文件不经过前端 | ✓ |

**结论（直接说）**：

- ❌ **2核2GB 入门型（45元/月）不能用** —— 冷启动/状态丢失时的全量重算峰值 3.3GB > 2GB，会被 OOM killer 杀掉。别买。
- ⚠️ **2核4GB**：日常增量撮合毫无压力（<1GB），只有**首次启动**或 `state.json` 丢失时会撞 3.3GB 峰值。**配 4GB swap** 即可兜住那次峰值（慢几十秒，不会失败），性价比可以接受。
- ✅ **推荐 4核8GB**：无任何压力，跑批快，未来想在服务器上跑回测/寻优也有余量。
- 磁盘若预算允许可上 60GB（回测产物是只增不减的，一年后 3.8GB → 6-8GB 量级，40GB 也撑得住）。

### 1.2 实例创建方式（创建页四个选项怎么选）

| 选项 | 是否推荐 | 理由 |
|---|---|---|
| **使用应用镜像 → `Docker CE`** | ✅ **推荐** | 预装 Docker + Docker Compose，与本项目的 `deploy/docker-compose.yml` 部署方式完全对口，开机即 `docker compose up`；底座是 Ubuntu，还能正常 apt 装东西 |
| 使用基础操作系统镜像 → `Ubuntu Server 24.04 LTS` | 备选 | 想完全掌控环境时用；需要自己 `apt install docker.io docker-compose-plugin`（5 分钟的事） |
| 使用容器镜像 | ❌ | 那是"托管容器"玩法，镜像要推到云厂商仓库，绕远路 |
| 宝塔/Hermes Agent 等 AI 应用镜像 | ❌ | 与本项目无关；宝塔面板会和 compose 的运维方式打架 |

**创建参数清单**：

- 地域：**广州**（主人在深圳，延迟最低；可选城市里广州最近）
- 镜像：应用镜像 → **Docker CE**（基于 Ubuntu 22.04/24.04）
- 套餐：**4核8GB**（预算紧则 2核4GB + swap，见 §4.4）
- 系统盘：40GB 起步
- 登录方式：密钥对（比密码安全）

#### 2.2.1 Git Bash 没有 rsync 怎么办（已装可跳过）

Git for Windows（含便携版）默认不带 rsync，装到 `~/bin`（无需管理员权限）：

```bash
mkdir -p ~/bin /tmp/msrsync && cd /tmp/msrsync
BASE="https://repo.msys2.org/msys/x86_64"
# 下载 rsync + 4 个运行时依赖（popt 最容易被漏掉，缺了会静默 127）
for f in rsync-3.5.1-2 libzstd-1.5.7-1 liblz4-1.10.0-1 libxxhash-0.8.4-1 popt-1.19-1; do
  curl -sO "$BASE/$f-x86_64.pkg.tar.zst"
  /c/WINDOWS/system32/tar.exe --zstd -xf "$f-x86_64.pkg.tar.zst"
done
mkdir -p ~/bin
cp extracted/usr/bin/{rsync.exe,rsync-ssl,msys-lz4-1.dll,msys-xxhash-0.dll,msys-zstd-1.dll,msys-popt-0.dll} ~/bin/
echo 'export PATH="$HOME/bin:$PATH"' >> ~/.bashrc
rsync --version   # 输出 3.5.1 即成功；报 127 = 还缺 DLL，用 ldd ~/bin/rsync.exe 看缺哪个
```

版本号会随时间更新，包名在 <https://repo.msys2.org/msys/x86_64/> 检索。
ldd 排查法：`ldd ~/bin/rsync.exe | grep "not found"` → 缺哪个 DLL 就去仓库下对应包。

## 4.5 上线后的运行注意事项（2026-10-11 补，实测踩过的坑）

1. **不要与本地开发机同时跑补数**。baostock 的**每日 5 万次请求配额**与
   6 小时黑名单封禁（`10001011`）是**账号级**的 —— 两台机器各跑各的会互相挤配额，
   触发封禁后两边一起挂 6 小时。要在本地调试就先停服务器容器，或反之。
   项目内有配额保护：达到上限当天立即失败并告警（不会像以前那样逐只重试空转 1.9 小时）。
2. **每次重启容器都会触发启动补跑**（`scheduler.catch_up_on_startup=true`），
   实测 30~90 分钟（补停机期间漏掉的交易日行情）。重启后日志里一片
   "开始增量回补"属**正常**，不是故障。补跑期间前端跑批会被明确拒绝
   （返回"启动补跑正在进行中"），不会再出现抢锁失败误推"跑批失败"告警。
3. **服务器上不能跑回测/参数寻优**（架构有意为之）：回测 API 只有**读**接口，
   5 个定时任务全都不含重计算；回测与寻优走**本地 CLI**。
4. **盯两个监控**：系统页的基本面陈旧度（直接查原始数据的公告日，超过 120 天标红）
   与行情覆盖率闸门（每日要求覆盖 ≥3000 只，达标才允许算净值）。
5. **`state.json` 是增量撮合的命门**：丢了会自动回退全量重算（正确行为，
   但 2核4GB 上会撞 3.3GB 峰值 → 靠 swap 兜）。别手工删
   `data/paper/default/` 下的文件。

## 5. 基本面周频回补的设计说明（2026-10-10 新增；2026-10-11 修正续传语义）

**任务**：`fundamental_weekly`，**每周一 06:00**，子进程跑
`python -m tools.backfill_fundamental --stale-days 6`（12h 超时上限 → 18:00 前结束）。

**为什么效果上仍是"每周全量刷新"**（主人拍板：一次性补完、接受长时间运行）：
三大报表/财务指标接口只能全量分页拉取（20~25 页/次），东财没有
"是否有新数据"的廉价探测接口 —— **做不到"没有就不拉"**。落盘
`save_fundamental` 按 [report_date, notice_date] 去重，因此：

- **数据效果 = 有更新则补上、没有则不变**（操作上是全量，结果上是增量）；
- 上一次成功是 7 天前（`7 > 6`）→ 本周照常全部重拉；
- **批量数据集**（业绩报表/业绩预告/股东户数/分红送配/基金持仓）按报告期记录，
  没有新报告期时自动"没有待办"直接跳过 —— 这部分**天然符合"没有则不做操作"**；
  （且只扫**法定披露截止日已过**的报告期，避免刚结束的季度被拿到残缺截面）
- 单次全量 ~9h（本地实测），06:00 起跑不占交易时段。

**★ 2026-10-11 修正：为什么用 `--stale-days 6` 而不是 `--force`**
原调度器传 `--force`，而 `--force` 会让「状态 ok 就跳过」这条判据彻底失效 ——
每只标的每次都进待办，**"断点续传"名存实亡**。实测全量 9h、watchdog 上限 12h，
余量只有 3h：一旦超时被杀，周二手动重跑又是从头 9 小时，同样大概率超时 →
最后几只标的永远拉不到。`--stale-days 6` 对"每周全量刷新"效果等价，
但本轮已完成的标的 `updated_at` 是今天、不再入待办 → **超时重跑只补没做完的那部分**。

**若将来改成"每周轮转 1/4"**：用 `--shard-count 4 --shard-index 0..3`（稳定哈希分片），
别用 `--stale-days 30` —— 全量跑批会把所有标的的 `updated_at` 刷成同一时刻，
`--stale-days N` 于是退化成「全动或全不动」的齐步振荡，永远形不成 1/4 轮转。

**已知的取舍**（写在注释里了）：
- 每周对东财发起一次全量请求（聚合 ~0.7 req/s × 9h，与首跑一致 —— 工具设计上限之内）；
- 已加入 `_NO_CATCH_UP_JOBS`：9 小时级任务不参与启动补跑，错过等下周一
  （代价：周一 07:00 后才启动服务，这一周零基本面更新 —— 要留意系统页的
  基本面陈旧度监控，它现在直接查**原始数据**的公告日，超过 120 天会标红）。

**2核2GB 专项结论**：模拟盘跑批日常走**增量撮合**（窗口 121 交易日，实测几百 MB），
但冷启动 / `state.json` 丢失时会**自动回退全量重算**，峰值实测 **3383MB**
（psutil 采样，全市场全区间）。这个峰值避不开，2GB 套餐 OOM 必现，
最低 **2核4GB + swap**，推荐 4核8GB。
