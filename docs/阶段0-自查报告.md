## 1. 🔴 P0 必修（破坏数据正确性红线）

### P0-1 · 时间锁可被绕过（两个入口实测泄漏未来数据）

`data_store` 的全局 `READ_UNTIL` 时间锁，是防止回测/模拟盘读到未来数据的**唯一屏障**（技术架构 5.4 节明确列为"红线"）。但它有两个绕过口：

```python
# read_quotes 里的实现
if end_date:
    _apply_read_until(start_date or "1900-01-01", end_date)   # ← 只在 end_date 非空时校验
```

**实测结果**：

| 调用方式 | 时间锁 | 实际返回 | 是否越界 |
|---|---|---|---|
| `read_quotes("sz.000004", "2020-01-01", None)` | `2024-06-30` | **1212 行，最晚到 2024-12-31** | ❌ 越界 6 个月 |
| `load_symbol_history("sz.000004")` | `2024-06-30` | **1212 行，最晚到 2024-12-31** | ❌ 越界 6 个月 |
| `read_quotes("sh.600519", "2024-12-01", "2024-12-31")` | `2024-12-15` | 抛出 `ReadUntilViolation` | ✅ 正确拦截 |

**影响**：回测里只要有一处写成 `read_quotes(sym, start)` 而不传 `end_date`，就能读到未来行情。策略会"知道明天涨什么"，回测收益完全虚高，**而且不报错、不警告，静默发生**。

**修法**：没有 `end_date` 时，若存在时间锁则用锁值作为上界（安全截断 + warning 日志）。

```python
# 改后
lock = get_read_until()
if end_date:
    _apply_read_until(start_date or "1900-01-01", end_date)
elif lock:
    end_date = lock                # 安全截断，绝不读到锁之后
    logger.warning(f"未指定 end_date，按时间锁截断到 {lock}")
```

**同一类问题还有一处**：`read_factor()` 也只有 `if end_date:` 才校验。同样修法。

### P0-2 · `read_quotes(symbols=[])` 静默返回全市场

```python
if symbols is not None and len(symbols) > 0:
    ...  # 精确读指定文件
else:
    ...  # 读全市场 glob  ← 空列表掉进了这里
```

**实测**：传空列表 → 返回 44 行（当前只有 2 个数据文件时的全市场）。
生产环境下拉满 5000 只股票后，传空列表会**读取整个全市场**，耗时从毫秒级变成秒级甚至更久。

**影响**：`build_universe` 这类逻辑里，如果某天候选池算出来是空的（比如全部被 ST/停牌过滤掉），传 `[]` 进去会意外拿到全市场股票，**静默地把"今天不该买入"变成"今天买一切"**。这是最难查的一类 bug。

**修法**：

```python
if symbols is not None:
    if len(symbols) == 0:
        return pd.DataFrame()      # 明确要 0 只 → 返回空
    ...  # 精确读
else:
    ...  # None = 确实是"全市场"，保留原语义
```

## 2. 🟠 P1 应修（写了但没接上，机制形同虚设）

这四项是同一类问题：**工具写得很完整，但没有任何调用点**。用引用计数扫出来的：

| 机制 | 定义处 | 实际调用次数 | 后果 |
|---|---|---|---|
| `with_retry` 重试装饰器 | `base.py:147` | **0** | 批量拉 5000 只股票时遇到网络抖动直接失败，无重试 |
| `_cache_get` / `_cache_set` | `base.py:274,277` | **0** | 最该缓存的 `fetch_spot()`（全市场 5000+ 行）每次调用都真打网络 |
| `_rate_limit()` 限流 | `base.py:271` | **baostock 6 次 / akshare 0 次** | **akshare 完全不限流** —— 而 akshare 才是更容易被东财/新浪限频的那个 |
| `log_datasource_call` | `meta_repo.py:108` | **0** | `datasource_log` 表永远是空的，**数据源失败/超时/限频完全无法排查** |

**为什么 akshare 零限流特别严重**：阶段 1 要"在线试跑"40~60 个接口，用户连着点几下就能触发东财限频；阶段 2 要拉 5000 只股票的历史数据。没有节流，很容易被封 IP。而我在 `base.py` 里写好了 `RateLimiter`，还在 `config.yaml` 里配了 `min_interval: 0.12`，就是没接到 akshare 上。

**修法**：
1. akshare 的每个对外方法（`fetch_daily` / `fetch_index_daily` / `fetch_trade_dates` / `fetch_spot` / `call`）开头加 `self._rate_limit()`
2. `fetch_spot` / `fetch_trade_dates` 加 TTL 缓存（分别 60s / 1 天）
3. 在 `BaseDataSource._call_with_log()` 里统一包一层重试 + 调用日志，而不是靠装饰器散落各方法

## 4. ⚪ 待明确（需要你拍板）

### W-1 · 交易日历偏移的语义（会影响模块 3 的持有期计算）

实测 `calendar.trading_day_offset("2024-01-02", "2024-01-05")` 返回 **4**（含首尾两端）。

但策略规格里写的是"**持有满 10 个交易日**强制卖出"。那么：
- 买入日当天算第 1 个交易日 → 用 `offset >= 10`
- 还是买入日之后才算 → 用 `offset > 10`（即 >= 11）

**差一天，对短持有期策略（10 天上限）是 10% 的误差。** 这个必须在写引擎前定死，否则回测结果会偏。

**我的建议**：买入当日（T+1 成交日）算第 1 个交易日，`offset >= 10` 触发卖出。即 **T+1 买入 → T+10 卖出**，实际持有 10 个交易日。

### W-2 · 是否需要为 akshare 加强制熔断

akshare 是阶段 1 的"试跑"入口，用户会反复点击。当前设计是"同 IP 10 次/分钟"限频。但**如果东财已经把你限了**，继续请求会加重封禁。是否需要：

- 还是只做限频，超了就报错让用户自己重试

**我的建议**：加熔断。实现成本很低（一个时间戳 + 状态标记），但能避免 IP 被长期封。

| `end` 显式且 ≤ 锁 | 原样通过 | — |

并新增 `_guard_day()` 覆盖 `read_universe`（股票池快照隐含"当日哪些股票可交易"，同属未来信息）。

**额外发现并修复：`build_universe` 在候选集清空时崩溃**

写测试时发现的真 bug：`DataFrame.apply(fn, axis=1)` 在**空 DataFrame** 上返回的是

`_mask_not_limit_locked` / `_mask_listed_days` / `_mask_rebuy_allowed`），
并在每个过滤步骤后加空表短路。单行纯函数保留不动（服务于"查单只股票"场景）。

### 7.3 P1 修复（4 项静默失效 + 1 个重试漏洞）

**统一入口**：新增 `BaseDataSource._invoke()`，把

**额外发现并修复：重试白名单有继承性漏洞**

```python
# 修复前
_RETRYABLE_EXCEPTIONS = (DataSourceError, ConnectionError, TimeoutError)
```

白名单里的 `ConnectionError` 是**内置**异常，而 akshare 底层抛的是
`requests.exceptions.ConnectionError` —— **两者没有继承关系**，
导致所有真实网络错误都静默地不重试。

修复为**黑名单**策略（枚举"不值得重试"的少数几类，其余默认重试），
因为第三方库的异常类型（requests / urllib3 / pandas / 裸 OSError / socket）**无法穷尽**：

```python
_NON_RETRYABLE_EXCEPTIONS = (DataSourceRateLimited, InvalidParamError,
                             SymbolFormatError, ConfigError, NotConfiguredError)
# DataSourceError → 重试；其余 AppError → 不重试；第三方库异常 → 默认重试
```

**并且限制频不重试** —— 被限频后立刻重试等于持续撞墙，由熔断器静默处理。

### 7.4 新增：akshare 限流与熔断（`throttle.py`）

| 机制 | 参数 | 说明 |
|---|---|---|
| `SlidingWindowRateLimiter` | akshare: `min_interval=1.0s`、`max_calls_per_minute=30` | 双约束同时生效 |
| | baostock: `min_interval=0.12s`、不限次数 | baostock 更稳定，无需严格限流 |
| `CircuitBreaker` | `definite` 档（429 / 频率超限）→ **300s** | 服务端明确告知超速 |
| | `soft` 档（`RemoteDisconnected` / `Connection aborted`）→ **60s** | 服务端掐连接，证据弱，冷却短 |

**安全上限 1800 次/小时** → 拉 5000 只股票日线约需 **2.8 小时**。这个代价是必要的。

**分两档的理由**：东财/新浪限频时常常**直接掐断连接**而不返回 429。
算作 `definite` 会让一次偶发闪断拖垮整个 3 小时补数据任务；算作普通网络错误又会持续撞墙。

## 9.1 🔴 我引入的回归：`calendar.refresh()` 变成了"假刷新"

**这是我上一轮加缓存时引入的，不是阶段 0 原有问题。**

`refresh()` 内部固定调用 `fetch_all_trade_dates("1990-01-01")`，而该方法现在被 `_invoke`
以 **1 小时 TTL** 缓存（`cache_key="bs:calall:1990-01-01:<今天>"`）。

**实测证据**（包装 `_fetch_all` 统计真实网络读取次数）：

| 调用 | 签名 | 真实网络读取次数 | 返回 |
|---|---|---|---|
| `calendar.refresh()` 第 1 次 | `(self)` | **1** | 13057 天 / 8728 交易日 |
| `calendar.refresh()` 第 2 次 | `(self)` | **仍然是 1** | 完全相同的数据 |

```python
# 现状：没有任何绕过缓存的手段
def refresh(self) -> dict[str, Any]:
    df = fetch_all_trade_dates("1990-01-01")   # ← 会被缓存 1 小时
    ...
    meta_repo.set_meta_bulk({... "calendar_synced_at": now ...})  # ← 时间戳照样更新
```

**为什么是个真问题**：`POST /api/v1/system/calendar/refresh` 返回"已同步"并写入新的
`calendar_synced_at`，但**根本没连数据源**。日历本身是低频数据，所以危害有限；
但"接口报告的动作与实际不符"是会掩盖故障的那类问题——
如果哪天数据源真的坏了，点刷新也看不出异常。

**修法**（很小）：给 `fetch_all_trade_dates` / `fetch_trade_dates` 加 `force_refresh: bool = False`，
透传到 `_invoke(..., bypass_cache=force_refresh)`；`calendar.refresh()` 传 `True`。
顺带给 `/refresh` 接口返回 `cache_bypassed: true` 并写 `datasource_log`，做到可观测。

## 9.4 🟡 缓存无法缓存返回 `None` 的函数

`TTLCache.get()` 用 `None` 表示"未命中"，而**被缓存的值本身也可能是 `None`** —— 两者无法区分。

**实测**：

| 被缓存函数的返回值 | 连续调用 3 次的真实调用次数 | 期望（若缓存正常） |
|---|---|---|
| `None` | **3** | 1 ❌ |
| `DataFrame` | **1** | 1 ✅ |

**实际影响**：现有方法都返回 `DataFrame` / `list`，**无实害**。但
`AkshareClient.call()` 是全系统唯一接受任意参数的入口，akshare 里存在返回 `None` 的接口 ——
那时会静默退化为"不缓存"，而不是报错。属于**降级安全**，但值得修干净。

**修法**：加哨兵对象 `_MISS = object()`，`get()` 返回 `_MISS` 表示未命中。

### 9.12.5 一条值得记住的经验

**"缓存"是个会改写语义的优化。** 加缓存时不能只看"数据还对不对"，
必须回头逐个检查**语义上承诺了动作的方法**：`refresh` / `resync` / `probe` / `reload` /
`check_now` 这类名字，只要内部读的数据被缓存了，就会变成"报成功但没做事"。

**识别方式**：包装底层调用数真实次数，**连续调用两次看计数是否递增** ——
纯静态扫描永远发现不了这类问题。
