# 腾讯云部署指南

> 目标：把本项目（FastAPI 后端 + Vue3 前端 + 本地数据仓库）部署到腾讯云轻量应用服务器，
> 用 `deploy/` 下的容器编排一条命令起服务。2026-10-10 编写。

---

## 1. 实例选型（先看结论）

### 1.1 硬件要求（实测依据）

| 维度 | 需求 | 实测/依据 | 结论 |
|---|---|---|---|
| **内存** | **≥ 4GB（推荐 8GB）** | 全市场回测引擎峰值 RSS **3383MB**（quality_reversal，2025-01~2026-09 全区间，psutil 实测）；这是每晚 23:00 模拟盘跑批的固定动作 | ⚠️ 硬门槛 |
| CPU | 2 核起步 | 跑批是 IO 型为主（东财/baostock 分页拉取），本地 2 核量级全量重算 ~1-2 分钟 | 2 核够 |
| 磁盘 | 40GB 够 | `data/` 当前 3.8GB（2.9 万 parquet）+ Docker 镜像 ~1.5GB + 系统 ~4GB，剩余 >30GB；回测产物日增 ~几 MB | ✓ |
| 带宽 | 3Mbps 够 | 单用户使用；前端首载 gzip ~1.2MB ≈ 4s；数据文件不经过前端 | ✓ |

**结论（直接说）**：

- ❌ **2核2GB 入门型（45元/月）不能用** —— 引擎峰值 3.3GB > 2GB，每晚 23:00 跑批必被 OOM killer 杀掉。别买。
- ⚠️ **2核4GB**：贴着上限跑（3.3 + 系统 0.4 + uvicorn 常驻 0.2 ≈ 3.9GB）。**必须配 2-4GB swap** 才稳妥，且内存紧张时跑批变慢。省钱可选，不推荐。
- ✅ **推荐 4核8GB**（轻量约 112 元/月档）：无压力，跑批快，未来跑回测/寻优也有余量。
- 磁盘若预算允许可上 60GB（回测产物是只增不减的，一年后 3.8GB → 6-8GB 量级，40GB 也撑得住）。

### 1.2 实例创建方式（创建页四个选项怎么选）

| 选项 | 是否推荐 | 理由 |
|---|---|---|
| **使用应用镜像 → `Docker CE`** | ✅ **推荐** | 预装 Docker + Docker Compose，与本项目的 `deploy/docker-compose.yml` 部署方式完全对口，开机即 `docker compose up`；底座是 Ubuntu，还能正常 apt 装东西 |
| 使用基础操作系统镜像 → `Ubuntu Server 24.04 LTS` | 备选 | 想完全掌控环境时用；需要自己 `apt install docker.io docker-compose-plugin`（5 分钟的事） |
| 使用容器镜像 | ❌ | 那是"托管容器"玩法，镜像要推到腾讯云仓库，绕远路 |
| 宝塔/Hermes Agent 等 AI 应用镜像 | ❌ | 与本项目无关；宝塔面板会和 compose 的运维方式打架 |

**创建参数清单**：

- 地域：**广州**（主人在深圳，延迟最低；可选城市里广州最近）
- 镜像：应用镜像 → **Docker CE**（基于 Ubuntu 22.04/24.04）
- 套餐：**4核8GB**（预算紧则 2核4GB + swap，见 §4.4）
- 系统盘：40GB 起步
- 登录方式：密钥对（比密码安全）

## 2. 一次性准备

### 2.1 安全组 / 防火墙

轻量服务器控制台 → 防火墙 → 添加规则：

| 端口 | 用途 | 来源 |
|---|---|---|
| 22 | SSH | 自己的 IP（限源更安全） |
| 8080 | 前端（nginx 容器对外） | 0.0.0.0/0 |
| 8000 | **不要开** —— backend 只绑定 127.0.0.1，由 nginx 反代 | — |

### 2.2 上传代码与数据

```bash
# 本地（Git Bash）：打包数据卷（约 3.8GB，3Mbps 上传约 1.5~3 小时，一次性成本）
cd F:/股票投资服务
tar czf data-backup.tgz data/
scp data-backup.tgz ubuntu@<服务器IP>:/home/ubuntu/

# 代码：走 git（服务器 git clone），或同样 scp 打包（排除 .venv/node_modules）
```

服务器上解压到部署目录（约定 `/opt/stock`）：

```bash
sudo mkdir -p /opt/stock && sudo chown ubuntu:ubuntu /opt/stock
# git clone 或 scp 代码到 /opt/stock
cd /opt/stock && tar xzf ~/data-backup.tgz    # → /opt/stock/data/
```

### 2.3 环境文件

```bash
cd /opt/stock
cp .env.example .env   # 若无 example，按本地 .env 手工创建（企微 webhook key 等）
chmod 600 .env         # compose 的 env_file 必须存在，否则 up 直接报错
```

## 3. 启动与验证

```bash
cd /opt/stock
docker compose -f deploy/docker-compose.yml up -d --build   # 首次构建 ~5-10 分钟
docker compose -f deploy/docker-compose.yml ps              # 两容器 healthy
docker compose -f deploy/docker-compose.yml logs -f backend # 看 app 启动与调度注册日志
```

启动日志里应看到（存在 ≠ 生效，逐条核对）：

```
已注册任务 paper_daily（模拟盘日度跑批）→ 每周一至周五 23:00
已注册任务 paper_intraday_check（模拟盘盘中清仓预警）→ 每周一至周五 14:45
已注册任务 alert_daily_summary（每日持仓早报）→ 每周一至周五 08:00
已注册任务 catalog_check（接口目录自检）→ 每周一至周五 09:00
已注册任务 fundamental_weekly（基本面/财务周频回补）→ 每周一 06:00   ← 2026-10-10 新增
```

浏览器验证：`http://<服务器IP>:8080` → 模拟仿真页净值曲线正常、策略回测列表正常。

### 3.1 调度时刻表（容器内 TZ=Asia/Shanghai，Dockerfile 已固化）

| 时间 | 任务 | 说明 |
|---|---|---|
| 每天 23:00 | `paper_daily` | 行情增量回补 → 快照 → 因子重算 → 净值全量重算（内存峰值 3.3GB 都在这一步） |
| 周一~五 14:45 | `paper_intraday_check` | fuyao 实时价清仓预警（企微） |
| 周一~五 08:00 | `alert_daily_summary` | 持仓早报（企微） |
| 每日 09:00 | `catalog_check` | 数据源接口目录自检 |
| **每周一 06:00** | **`fundamental_weekly`** | **基本面/财务周频回补（一次性补完 ~9h，2026-10-10 新增，见 §5）** |

## 4. 日常运维

```bash
# 更新发版
cd /opt/stock && git pull
docker compose -f deploy/docker-compose.yml up -d --build

# 看跑批日志（最近的 job 执行记录在系统状态页 / meta.db 的 job_run_log）
docker compose -f deploy/docker-compose.yml logs --tail 200 backend

# 手动触发跑批：前端「模拟仿真 → 立即跑一次」，或
curl -X POST http://127.0.0.1:8000/api/v1/paper/accounts/default/run
```

### 4.1 备份（数据无价）

```bash
# crontab：每周日 03:00 打包 data/（含 SQLite meta.db、行情、因子、模拟盘产物）
0 3 * * 0 cd /opt/stock && tar czf ~/backups/stock-$(date +\%F).tgz data/ && find ~/backups -mtime +30 -delete
```

### 4.2 时区

后端镜像已固化 `TZ=Asia/Shanghai`（`deploy/Dockerfile.backend`），调度 cron 全按北京时间跑；
**改动调度时间只改 `backend/config/config.yaml` 的 `scheduler.jobs.*`**（挂载卷 `:ro`，改完 `docker compose restart backend`）。

### 4.3 手动补数（CLI 进容器）

```bash
docker compose -f deploy/docker-compose.yml exec backend bash
python -m tools.backfill_quotes --incremental --end 2026-10-10   # 行情
python -m tools.backfill_fundamental --status                     # 基本面进度（不联网）
python -m tools.backfill_fundamental --stale-days=7               # 基本面强制周刷
python -m tools.backfill_universe --start 2026-10-01 --end 2026-10-10 --force
```

### 4.4 若选了 2核4GB：必须配 swap

```bash
sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

## 5. 基本面周频回补的设计说明（2026-10-10 新增，同日改为一次性补完语义）

**任务**：`fundamental_weekly`，**每周一 06:00**，子进程跑
`python -m tools.backfill_fundamental --force`（12h 超时上限 → 18:00 前结束）。

**为什么是 `--force` 全量重拉**（主人拍板：一次性补完、接受长时间运行）：
三大报表/财务指标接口只能全量分页拉取（20~25 页/次），东财没有
"是否有新数据"的廉价探测接口 —— **做不到"没有就不拉"**。落盘
`save_fundamental` 按 [report_date, notice_date] 去重，因此：

- **数据效果 = 有更新则补上、没有则不变**（操作上是全量，结果上是增量）；
- **批量数据集**（业绩报表/业绩预告/股东户数/分红送配/基金持仓）按报告期记录，
  没有新报告期时自动"没有待办"直接跳过 —— 这部分**天然符合"没有则不做操作"**；
- 单次全量 ~9h（本地实测），06:00 起跑不占交易时段；状态文件断点续传，中断重跑即续上。

**已知的取舍**（写在注释里了）：
- 每周对东财发起一次全量请求（聚合 ~0.7 req/s × 9h，与首跑一致 —— 工具设计上限之内）；
- 已加入 `_NO_CATCH_UP_JOBS`：9 小时级任务不参与启动补跑，错过等下周一；
- 比早先的 `--stale-days` 轮转方案更简单直接：不依赖状态时间戳，每周一市场必然全量最新。

**2核2GB 专项结论**：模拟仿真跑批（paper_daily 每晚 23:00）本身就是
引擎全量重算 —— 峰值内存实测 **3383MB**（psutil 采样，2025-01~2026-09 全市场）。
**"不做新策略回测"避不开这个峰值，2GB 套餐 OOM 必现，最低 2核4GB+swap，推荐 4核8GB。**
